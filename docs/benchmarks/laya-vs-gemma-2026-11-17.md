# LAYA 전환 실측: 기존 Gemma 평가와 비교

H2O와 배치 설정, 순서 안정성까지 포함한 최신 결론은 [종합 비교](decision-models-summary-2026-11-17.md)를 참고하세요.

측정일: 2026-11-17 KST. 기준 코드: `bcd5ca3`.

같은 한국어 A/B 문구와 같은 Nemotron 페르소나를 사용했을 때 기본 24건 작업은 기존 Ollama/Gemma의 **88.995초에서 LAYA CUDA의 16.114초로 감소**했습니다. 이 실행에서 전체 처리 속도는 **5.52배**, 소요 시간 감소는 **81.9%**였습니다.

판정은 동일하지 않았습니다. 24명 중 개별 winner가 같은 것은 **8명(33.3%)**이었고, 최종 추천은 LAYA가 A, Gemma가 B였습니다. 사람의 정답 라벨이 없어 어느 모델이 더 정확한지는 판단할 수 없습니다. 검토자의 결론은 **빠른 사전 평가의 운영 가능성은 확인했으나, 최종 마케팅 판정기로 단독 채택할 근거는 부족하다**입니다.

## 접수부터 완료 리포트까지

클라이언트의 단조 시계로 HTTP 제출부터 `completed` 관측까지 측정했습니다. 검색·모델 로딩·큐 대기·평가·집계를 포함하며 완료 관측 오차는 약 0.5초입니다. 별도 수동 종합 분석은 실행하지 않았습니다.

| 실행 | 기존 Gemma | LAYA CUDA | Gemma/LAYA |
| --- | ---: | ---: | ---: |
| 첫 8명 작업 | 39.242초 | 14.106초 | 2.78배 |
| 8명 재실행 | 37.220초 | 14.620초 | 2.55배 |
| 기본 24명 | 88.995초 | 16.114초 | 5.52배 |

최종 LAYA 측정은 구매 질문을 보정한 뒤 워커를 재시작하여 수행했습니다. 두 평가기의 첫 작업 모두 API의 검색 모델·인덱스 캐시는 이미 사용한 상태였고, LAYA 모델/Ollama 모델은 해당 실행에서 처음 로드했습니다. 프로세스 모델 로딩과 OS 디스크 캐시를 분리한 실험은 아닙니다. 비교의 주 지표는 재실행 8명/24명입니다.

24명에서 검색·태스크 준비는 두 평가기 모두 약 9.6초였습니다. 첫 실행 상태 관측부터 완료까지 평가 구간은 LAYA 약 6.0초, Gemma 약 78.9초였습니다. 이는 모델 커널만의 시간과 다릅니다. LAYA에서는 현재 전체 시간의 상당 부분이 페르소나 검색에 쓰입니다.

LAYA 40건, Gemma 40건은 모두 완료됐고 실패 태스크는 없었습니다. 각 표본 크기에서 실행 수가 적고 문구는 한 쌍이므로, 일반적인 처리량이나 지연 분포를 입증한 결과는 아닙니다.

## 결과·기능 비교

| 항목 | 기존 Gemma | LAYA |
| --- | --- | --- |
| 점수 방식 | 한 번의 생성 응답으로 A/B의 4지표를 0~100 평가 | 각 안·지표의 긍정/부정 선택 확률을 두 순서로 평균 후 0~100 환산 |
| 표본당 판단 | 생성형 호출 1회 | `predict` 2회, 총 16개 choice 질문 |
| 근거 | 모델이 생성한 설명 | 가중 점수의 숫자 요약 |
| 이미지 | 비전 모델 선택 시 지원 | 이 multilingual 체크포인트는 텍스트용 |
| 8명 반복 | winner 6/8 일치, 전체 점수 동일 0/8 | winner 8/8 일치, 전체 점수 동일 8/8 |

LAYA 반복 비교에서는 Chroma 메타데이터 키 정렬을 적용했습니다. 정렬 전에는 같은 값이라도 DB가 반환한 키 순서 때문에 모델 입력·점수가 변했습니다. 정렬 회귀 테스트와 실제 CUDA 재추론으로 수정 효과를 확인했습니다. Gemma 반복의 변동 원인을 메타데이터 순서·샘플링·실행 수치 특성별로 분리한 실험은 하지 않았습니다.

| 비교 표본 | 개별 winner 일치 | LAYA 최종 추천 | Gemma 최종 추천 |
| --- | ---: | --- | --- |
| 첫 8명 | 4/8 (50%) | A | B |
| 8명 재실행 | 6/8 (75%) | A | B |
| 24명 | 8/24 (33.3%) | A | B |

LAYA의 확률 환산 점수와 Gemma의 생성형 평점은 의미가 다릅니다. 일치율은 기존 모델을 정답으로 놓은 정확도가 아닙니다. 둘 다 실제 고객 전환율의 관측값이 아닙니다.

24명 LAYA의 encoder 입력 토큰 합계는 282,704, 생성 토큰은 0이었습니다. Gemma는 prompt 18,254, completion 21,115였습니다. LAYA 입력은 질문마다 반복 인코딩한 합계이며 서로 다른 토크나이저·계산 방식이므로 토큰 수를 처리량이나 비용 비교로 직접 환산하지 않습니다.

## 사례를 읽고 내린 판단

다음은 합성 페르소나를 읽은 검토자의 해석이며, 실제 고객 반응의 정답 라벨이 아닙니다.

- **소득이 낮고 꼼꼼한 30대 개발자:** LAYA A, Gemma B. 제품 효용을 확인할 수 있는 무료 체험 A를 선호할 개연성이 있습니다. Gemma의 “소득 증대 중시 → 즉각 할인 선호” 설명은 무료 체험이 줄이는 지출·실패 위험을 비교하지 않았습니다. 이 사례에서는 A 쪽이 더 설득력 있으나 해지·자동 결제 조건이 없어 확정할 수 없습니다.
- **신규 소프트웨어 도입에 보수적인 49세 편집자:** 두 모델 모두 B. 보정 후에도 LAYA의 B 구매 의도는 88, Gemma는 80입니다. 페르소나는 기존 작업 체계를 고수합니다. 할인만으로 새로운 구독에 높은 의향을 부여한 것은 과도해 보이며, 두 모델 모두 업무 전환 비용을 충분히 반영했는지 의문입니다.
- **제조업 효율을 중시하는 30대 컨설턴트:** 최종 LAYA와 Gemma 모두 B. 초기 어댑터는 구매 의도를 “이용하려 하는가”로 물어 A의 구매 점수를 99로 줬습니다. 유료 구매·지불 의향으로 보정하자 A 79, B 96이 되었습니다. 이는 모델 우열보다 측정 개념을 먼저 명확히 해야 함을 보여 줍니다.

최종 수치는 구매 의도를 **유료 구매·유료 구독에 지불할 의향**으로 고친 v2만 사용했습니다. 무료 체험 시작과 결제는 다른 행동이므로 이 정의 보정은 필요한 수정입니다. 질문 보정만으로 24명 중 6명의 LAYA winner가 바뀌었습니다. 기존 Gemma의 결과에 일치하도록 튜닝한 것이 아니며, 실제로 보정 후 전체 일치율은 50%에서 33.3%로 낮아졌습니다.

문구에는 가격, 할인 유지 기간, 무료 체험의 자동 결제·해지 조건, 신규/기존 고객 여부가 없습니다. 따라서 두 모델이 서로 다른 가정을 세울 여지가 큽니다. **속도와 반복 일관성은 LAYA의 확인된 장점이고, 판정의 타당성은 미검증**입니다. 현 단계에서는 후보 문구 사전 선별과 불일치 사례 검토에 사용하고, 최종 승자는 명확한 전환 목표와 실제 사용자 데이터로 확인하는 것이 적절합니다.

## CPU 기록

LAYA CPU의 첫 8명 작업은 114.103초, 재실행은 104.834초였습니다. CPU 24명 작업은 CUDA 전환을 위해 중단했으므로 완료 시간은 없습니다. CPU는 FP32·키 정렬 보정 전, 최종 GPU는 FP16·보정 후 구성이므로 이 수치는 운영 참고용이며 통제된 커널 성능 비교가 아닙니다.

## 재현

모델·벡터 DB를 준비하고 [LAYA 실행 문서](../laya-evaluator.md)에 따라 API/워커/웹을 시작합니다. API 기본값을 사용한다면 `--api-base`를 생략할 수 있습니다. 이번 실측은 Next 프록시를 통과했습니다.

```bash
python scripts/benchmark_evaluators.py --evaluator laya \
  --api-base http://localhost:3000/_nemotron_api \
  --output outputs/benchmarks/laya.json
python scripts/benchmark_evaluators.py --evaluator openai \
  --api-base http://localhost:3000/_nemotron_api \
  --llm-model gemma4:e2b-it-q4_K_M \
  --output outputs/benchmarks/gemma.json
```

첫 실행에 모델이 이미 로드되어 있는지, CPU/GPU 디바이스·dtype, Ollama 적재 비율, 선택된 ID 집합을 함께 확인해야 합니다. 스크립트는 실제 작업을 생성하며 결과를 `outputs/`에 보관합니다. 이번 측정의 원본 큐·리포트도 로컬에 보관했습니다.
